# Plan v1: Full Ebook Reader App

Status: approved direction, pending spec + architecture (see workflow below).
Date: 2026-09-19. Supersedes the delivery route in PLAN_epub3_readalong.md
(the EPUB3 generator scripts are kept and reused as the TTS pipeline; the
reader is now our own app instead of Apple Books).

## Goal

Build a fully working ebook reader that meets the standards of commercially
available reading apps, with read-along voice driven by reading position.
Optimized for Italian and Danish books. Version 0 (tag `v0`) is the existing
CLI pipeline; this plan is version 1.

## Required features (acceptance targets)

1. **Library**: import EPUBs; list with title/author/cover; per-book reading
   progress persisted.
2. **Reading view**:
   - Fonts: family, size, weight, line-height.
   - Themes: light / dark / sepia minimum, ideally custom colors.
   - **Scrolling mode**: continuous scroll AND paginated, user-toggleable.
   - **Auto progression**: auto-advance (paginated) / auto-scroll (scroll
     mode), configurable speed.
3. **Voice by progression** (the core differentiator):
   - TTS reads from the current reading position; the spoken sentence is
     highlighted and the view follows the voice.
   - Manual scroll or tap repositions the voice ("tap-to-read-from-here").
   - Auto progression can be driven by the voice (advance when audio ends).
4. **Voice tuning**: engine + voice selection, rate, pitch; per-book voice
   cast (reuse the LLM speaker-tagging from `edge_reader.py`); a
   "test this voice" button.
5. **Language optimization**: Italian and Danish. The LLM text-preparation
   step (clean + repunctuate + speaker tagging) must work for both; the
   reader UI must handle CJK-free European typography well (hyphenation,
   quotes, dialogue dashes — Saramago's unmarked dialogue is the hard case).

## TTS engines (pluggable interface, benchmarked)

Build a `TTSEngine` interface with adapters; the app never calls an engine
directly.

| Engine | Italian | Danish | Cost | Notes |
|---|---|---|---|---|
| edge-tts (existing) | Yes (GiuseppeMultilingual + 3 native it-IT) | Yes (Christel, Jeppe) | Free | Current baseline; word-boundary timestamps already used by `epub_mo.py` |
| Gemini TTS (AI Studio key) | Yes | **Yes — verified 2026-09-19** (live synthesis test, both languages) | Free tier | Most expressive; style-controllable ("read as a warm narrator"). Models seen: gemini-2.5-flash-preview-tts, gemini-2.5-pro-preview-tts, gemini-3.1-flash-tts-preview. Output: raw PCM L16 24kHz mono |
| Google Cloud TTS | Yes | Yes (da-DK documented) | ~1M chars/month free (billing account required) | Documented Danish; WaveNet/Neural2 quality |

Engine choice per book is a setting. The benchmark deliverable (spec agent)
must include a small recorded-sample comparison harness the owner can run
locally with real API keys — the cloud sandbox has no keys and a 30s command
limit, so live synthesis never runs in the sandbox.

## Platform constraints (decided context, not open questions)

- The earlier plan rejected a web/PWA player because iOS Safari suspends web
  audio when the phone is locked. The owner accepts this trade-off for v1:
  the reader is a local-first web app served from the homelab (Docker),
  desktop-first, responsive on mobile. Lock-screen playback remains an
  open item for a future version (native shell / fixed-layout EPUB export).
- The spec agent may propose the modern stack (the owner asked for "more
  advanced" tech than the current plain-Python scripts), but must keep the
  Python TTS pipeline callable from the app (subprocess or service boundary).

## Multi-agent workflow

Work is split into four roles, run as separate sessions (Vibe Code Web or
CLI). Each role reads the previous role's output from the repo before
starting; if it is missing, do that role's job first or stop with a clear
note in the session — never fake upstream work.

| Role | Consumes | Produces |
|---|---|---|
| **A. Research & Spec** | README, PLAN files, this doc | `docs/SPEC_v1.md`: feature matrix vs Apple Books / Google Play Books / Readest / Moon+ Reader; TTS engine comparison with concrete API findings; acceptance criteria |
| **B. Architecture** | SPEC_v1 | `docs/ARCHITECTURE_v1.md`: stack choice with rationale, module breakdown, milestones M1–M4, test strategy |
| **C. Implementation** | ARCHITECTURE_v1 | The app, one PR per milestone |
| **D. Testing & QA** | each impl PR | `tests/` + `docs/QA_v1.md`: test plan, fixtures, validation harness results |

Milestones (suggested; architecture agent refines):

- **M1**: Library + reader view (fonts, themes, both scroll modes, progress).
- **M2**: TTS engine interface + edge-tts adapter + voice-by-progression
  (highlight sync, tap-to-read, voice-driven auto-advance).
- **M3**: Voice tuning UI + LLM preparation integration (Italian + Danish).
- **M4**: Docker deployment for the homelab + benchmark harness + docs.
